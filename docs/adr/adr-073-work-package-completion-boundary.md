# ADR-073: 作業パッケージの完了条件 — 生んだ運用問題を外へ押し出さない

## ステータス

試験運用 (2026-08-11)

> 本 ADR は [ADR-072](adr-072-nightly-todo-loop.md)（夜間 todo 消化ループ）の運用で確立した「WP をいつ閉じてよいか」の判断規則を、**他の作業パッケージへ再利用できる形**で切り出したものである。個別の WP の進捗は ephemeral な計画書が持ち、判断規則は本 ADR が持つ。

## コンテキスト

### 実装が終わっても運用は回らない

[ADR-072](adr-072-nightly-todo-loop.md) の夜間ループは 2026-08-08 に本番稼働へ入り、受け入れ基準に挙げた実装・スモークは充足していた。ところが 2026-08-10 に**人間が夜間 PR をマージする経路を初めて通した**ところ、運用問題が 5 件出た。

| 症状 | 由来 |
|---|---|
| `pnpm merge-pr` が夜間 PR を検出できない | 「bot が作った PR を人間がマージする」経路を WP-18 が新設したことで生まれた |
| post-merge feedback の進行中ガードが完了済み run を進行中と誤判定する | 以前から存在したが、連続マージという WP-18 の運用で毎回踏むようになった |
| 復旧コマンド `--feedback-only` が同じガードに阻まれる | 同上 |
| marker が危険な復旧手順を案内する | 同上 |
| CodeRabbit クォータが自律 PR と人間の作業で競合する | 決定 16 で自律 PR が毎晩 1 レビュー消費するようになったことで生まれた |

**これらは「実装の残り」ではない。** 実装は完了しており、動いてもいた。にもかかわらず、この 5 件を放置すると夜間ループの運用は成立しない（1 件目は採用率測定のたびに踏む）。

### 「実装完了 = WP 完了」で閉じると起きること

WP をここで閉じると、5 件は**どの WP にも属さない浮いたタスク**になる。todo には残るが、優先度の文脈（「これを直さないと WP-18 の受け入れ基準が測れない」）が失われ、他の一般タスクに埋もれる。実際 1 件目（順位 397）は**採用率測定の運用に直結**しており、放置すれば WP-18 の完了条件そのものが測定不能になっていた。

### かといって全部を紐づけると計画書が退役できない

一方で、WP の作業中に見つかった問題を**すべて**その WP に紐づけると逆の失敗が起きる。WP-18 の PR やその CI では、リポジトリ全体に適用する一般則（観測の完全性、重複実装の予防、shell / config パースの安全性など 8 件）や、別クレートの既存 flaky テストも見つかった。これらを WP-18 の完了条件に含めると、**一般則の整備が終わるまで ephemeral な計画書を削除できない**。計画書の退役条件は「全 WP が完了または見送り」であり、ephemeral 文書が永久に残ることは設計意図に反する。

## 決定 (試験運用)

### 1. 残作業を 3 区分に分ける

WP の残作業表は、**完了条件に効くかどうか**で区分する。1 つの表に混ぜると「この WP を閉じるのに何が要るのか」が読み取れなくなる。

| 区分 | 内容 | 完了条件 |
|---|---|---|
| (1) 観測待ち | 機構は整備済みで、事象か期限を待つもの | **含める**（ただし個別に非ブロッカー判定してよい） |
| (2) その WP が生んだ / その WP の運用で踏む問題 | 下記の判定基準を満たすもの | **含める** |
| (3) WP 外の派生 | その WP の作業中に見つかったが機構としては独立しているもの | **含めない** |

### 2. (2) の判定基準は 2 つ

| 基準 | 内容 |
|---|---|
| 基準 1 | **その WP の機構が無ければ起きなかった** |
| 基準 2 | 以前から存在したが、**その WP の運用で踏み、使い勝手に影響する**潜在バグ |

基準 2 を含めるのは、「元からあったバグだから WP の責任ではない」で押し出すと、**その WP を運用する限り毎回踏む問題**が誰の担当でもなくなるためである。WP が新たに踏ませたのなら、踏ませた側が決着させる。

### 3. (2) の決着は「対処」または「根拠つきの見送り」

すべてを直す必要はない。**見送りも正規の出口**であり、その場合は理由と移管先（todo の順位番号）を記録する。禁止するのは「無言で残す」ことだけである。

### 4. (3) は完了条件に含めないが、優先度を下げる意味ではない

(3) に分類したからといって後回しにしてよいわけではない。WP-18 では (3) のうち 2 件（flaky テストの解消、`cargo fmt` の機構的ブロック）を**高優先度で WP とは独立に着手する**と判断した。区分は**完了条件への紐づけ**を決めるものであって、優先度を決めるものではない。

## 帰結

### 利点

- **WP を閉じる条件が読み取れる**。残作業表を見れば「あと何が要るか」が (1) と (2) だけで完結する。
- **WP が生んだ運用の綻びが浮かない**。実装完了と運用成立を別の関門として扱える。
- **ephemeral 文書が退役できる**。一般則の整備を WP の完了条件から切り離したため、計画書の削除が一般則の進捗に人質を取られない。

### 欠点 / 留意点

- **区分の判定に主観が残る**。基準 2 の「使い勝手に影響する」は程度問題であり、境界例では判断が割れる。WP-18 では 5 件すべてが明確だったが、そうでない場合は WP のオーナーが決めて理由を残す。
- **(2) が膨らむと WP が閉じられなくなる**。運用問題が出続ける WP は、そもそも設計を見直す信号として扱うべきで、完了条件を緩めて閉じるのは筋が悪い。

### WP-18 での適用実績 (2026-08-11)

5 件すべてを 3 PR で決着させ、WP-18 の**残る完了条件**は (1) の採用率測定 1 本になった。**非ブロッカーの残作業 (スモーク未確定 3 件) は別に残っている**が、本区分の定義どおり完了条件には含めない — 「残作業がゼロ」と「完了条件を満たした」は別である。

| 順位 | 区分 / 基準 | 決着 |
|---|---|---|
| 397 | (2) 基準 1 | [ADR-013](adr-013-merge-pipeline.md) § PR 検出のフォールバックと逃げ道 |
| 398-400 | (2) 基準 2 | [ADR-030](adr-030-deterministic-post-merge-feedback.md) § 並行起動 guard / § run の特定は PR 番号で束縛する / § `.failed` marker の復旧手順 |
| 401 | (2) 基準 1 | [ADR-019](adr-019-coderabbit-review-hybrid-policy.md) § 無料枠の窓は固定時刻ではなく直近の消費に追随する（記録のみ） |
| 410 | (2) 基準 1 | [ADR-066](adr-066-autonomy-global-kill-switch.md) § 4 の例外と縛り |

**(2) の対処が (1) の測定を可能にした**という因果が実際に起きている。順位 397 を直すまで、夜間 PR のマージには毎回 `jj bookmark track` が要り、採用率測定の運用が成立していなかった。

## 試験運用判断基準 (ADR-039)

- **decision trigger**: WP-19 以降の作業パッケージ 2 つ以上で本区分を適用し、(a) 残作業表から完了条件が読み取れたか、(b) (2) に分類した項目が実際に WP の受け入れ基準へ効いたか、(c) (3) の切り離しで計画書の退役が妨げられなかったか、を確認する。
- **期限**: 2026-11-30。未判定なら延長 / 却下を判断する。
- **却下の形**: 区分が形式主義になり判断コストだけが増えるなら、「(2) と (3) を分けず、WP オーナーが個別に紐づけを決める」へ戻す。
