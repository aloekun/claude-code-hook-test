# ADR-090: todo 台帳の Tier はタスクの種類を表し、優先度は着手時に決める

## ステータス

採用 (2026-11-12)

> 順位 table (`docs/todo-summary*.md`)・台帳 (`docs/claude-code-web-tasks.md`)・詳細エントリの Tier は、post-merge feedback と同じ「種類」の分類 (1 = 決定論的な仕組み、2 = テスト/自動化、3 = ドキュメント/ルール) を表す。優先度は台帳に持たず、作業に着手するときにその時点の状況で決める。

## コンテキスト

### 同じ「Tier」に 2 つの意味が混ざっていた

post-merge feedback (analyze-pr / post-merge-feedback の SKILL.md、`aggregate-feedback` facet) は、再発防止策を種類で Tier 1〜3 に分ける。1 = hooks / linter (決定論的な防止)、2 = テスト / 自動化、3 = ドキュメント / ルール。

一方、順位 table の Tier 列と詳細エントリの「実行優先度: Tier N」は、優先度 1〜5 として使われてきた。こちらには、各 Tier が何を意味するかの定義がどこにも書かれていなかった。そのため起票のたびに「緊急ではない = Tier 3」と付けられ、feedback で Tier 2 (`test_addition`) だった提案が台帳では Tier 3 になっていた (順位 591 / 601 / 602 が該当。元レポートは `.claude/feedback-reports/609.md` / `616.md` / `617.md` / `625.md`)。2026-11-12 の時点で、順位 500 以降の Tier 3 34 行のうち約 21 行は、タスク名からテストや検査の追加と読める。

ユーザーは Tier 3 をドキュメント関連と理解しており、台帳の Tier を見て作業を選ぶと、想定と違うタスクを選ぶことになる。

jj の履歴で調べた結果 (2026-11-12)。いずれも、優先度の仕組みそのものを主目的にした PR ではない。ユーザーの指示が記録に残っているのは #197 の 1 件だけである。

### 台帳に置いた優先度は古くなる

ユーザーの指摘 (2026-11-12): どれだけ整えた優先度を用意しても、次に追加した 1 タスクが最優先だったとき、全体を振り直さない限り既存の優先度は古くなる。230 行の表で振り直しは現実的でなく、実際に一度も行われていない。着手するときに判断すれば、常にその時点の状況で順番を決められる。

## 決定

1. **Tier はタスクの種類を表す。** 値は Tier 1〜3 の 3 つで、post-merge feedback の分類と同じにする。

   | Tier | 種類 | 主な成果物 |
   |---|---|---|
   | Tier 1 | 決定論的に止める仕組み | PreToolUse / PostToolUse / Stop の hook、custom lint rule、`pnpm lint:*` の検査、push の品質ゲート、CI の必須検査 |
   | Tier 2 | テスト / 自動化 | テストの追加・修正、CI の step、exe / スクリプトの修正や機能追加 (実行されるコード) |
   | Tier 3 | ドキュメント / ルール | ADR、`docs/`、CLAUDE.md、SKILL.md、takt facet の instruction など、読み手の判断に委ねる文章 |

2. **種類の決め方**
   - 完了基準を満たすのに必要な主な成果物で決める。主な成果物が複数の種類にまたがり決めきれないときは、番号の小さいほうにする (決定論的な防止を優先する feedback の方針と同じ)
   - post-merge feedback / 週次レビュー由来のタスクは、元レポートの分類 (`test_addition` なら Tier 2 など) を写す。起票時に種類を変えるなら、詳細エントリに理由を書く
   - 調査タスクは、調査の後に作る見込みの成果物で決める
3. **Tier 4 / 5 は使わない。** 旧 Tier 5 の「再評価トリガー付きの見送り follow-up」([ADR-042](adr-042-rule-vs-mechanism-boundary.md) § 追記 (2026-09-13)) は、種類の Tier を付け、タスク列に「見送り follow-up」と書き、依存列に再評価トリガーを書く
4. **優先度は台帳に持たない。** 作業に着手するときに、ユーザーとエージェントがその時点の状況で決める。順位は追記型の ID であり、順序を表さない ([ADR-033](adr-033-todo-numbering-simplification.md) § 改訂 決定 1)。依存列は事実 (何が先に終わっている必要があるか) だけを書き、「最優先」「直近優先」のような優先度の記述は新しく書かない
5. **詳細エントリの「実行優先度」行は「種類」行に置き換える。** 形式は `> **種類**: Tier N — <種類を決めた理由>。工数 <XS/S/M/L>`
6. **名称は変えない。** 「推奨実行順序サマリー」「順位」の名称は、パーサ・リンク・本文の参照へ波及するため変えない。ADR-033 § 改訂 決定 5 と同じく、表記はそのまま意味だけを定義し直す
7. **`cli-docs-lint` の `priority-inversion` 検査を撤去する。** Tier の小さいタスクが大きいタスクに依存することを検出する検査だったが、Tier が種類になると、Tier 1 の lint rule が Tier 2 のテストに依存するのは正常な形である。撤去で対象ファイル (`priority_inversion.rs`) が無くなる順位 199 は、前提消滅として retire する
8. **既存の行は 3 本の PR で移行する。**
   - PR 1 (本 ADR): 定義と、優先度を前提にした仕組みの撤去
   - PR 2: 既存の行 (順位 table・台帳・詳細エントリ) の付け直しと、依存列に残る優先度の記述の除去
   - PR 3: 起票時に元レポートの種類と台帳の Tier が食い違わないことを検査する。起票の手順も元の種類を写す形に直す

   PR 2 が終わるまでは、既存の行の Tier は旧来の優先度のまま残る。PR 2 の前に既存の行の Tier を根拠に作業を選ばない。PR 2 は 2026-11-13 に付け直しを終えた (on-hold の行も含む)

## 帰結

### 利点

- ユーザーが Tier を見て想定どおりの種類のタスクを選べる
- feedback レポートの分類と台帳の値が一致し、起票のたびに判断する必要が無くなる
- 優先度の振り直しという、誰も行わない作業が無くなる

### 欠点 / 留意点

- 台帳を見ただけでは、次に何をすべきかが分からない。着手のたびに候補を選んで判断する手間がかかる。この手間は、古くなった優先度に従って誤ったタスクを選ぶコストより小さいと判断した
- [ADR-052](adr-052-autonomy-execution-boundary-classes.md) の自動実行可クラス「Tier 3 cleanup」は、旧来の Tier の語を名前に使っていた。種類の Tier 3 (ドキュメント) と取り違えないよう、「局所 cleanup」へ改名した ([ADR-067](adr-067-phase-b-unattended-fix-push.md) の参照も同様)
