# ADR-074: auto lane 選別基準 — 台帳のどの行を夜間ループに割り当てるか

## ステータス

試験運用 (2026-08-17)

> [ADR-072](adr-072-nightly-todo-loop.md) 決定 18 は台帳の無人可列を **lane（担当割り当て）** として定義したが、「どちらの lane に割り当てるか」の判断軸は暗黙のままだった。本 ADR はその判断軸を明文化する。決定 18 が lane の *意味* を、本 ADR が lane の *割り当て方* を担当する。

## コンテキスト

### lane を宣言にしたが、割り当ての基準が無かった

決定 18 により「台帳の `✅` は担当の宣言であり、条件の充足判定ではない」と整理された。宣言である以上、誰かが割り当てを決めなければならない。ところが実際に台帳を埋める段になると、判断は毎回その場の直観で行われていた。結果、台帳は 2026-08-16 時点で auto 行が 2 件しかなく、**夜間ループは作ったものの流す在庫が無い**状態になっていた。自動消化の機構を作った意味が失われていた。

### 直観による選別は 2 方向に外れた

在庫を積むために未掲載 236 件を選別したところ、最初の 2 回はいずれも失敗した。

**1 回目 — 過剰除外。** 順位表の「タスク」列と「依存」列に対してキーワードで除外をかけた。`ADR` という語で 88 件が落ちたが、このリポジトリの todo はほぼすべて参照欄に ADR 番号を書くため、実際に ADR を起票するタスクは 22 件しかなかった。**「ADR に言及する Rust テストタスク」まで巻き添えで消えていた。**

**2 回目 — 精査不足。** 1 回目の穴に気づいた後、再検査の対象を「タイトルがテスト系 かつ 工数が小さい かつ 除外語がタイトルに無い」に絞った。この絞り込み自体がまた順位表ベースだったため、拾えたのは数件で、残りは未検査のまま「human 担当で妥当」と報告してしまった。

共通する原因は、**順位表という要約の上で判定していたこと**である。順位表のタイトルと依存欄は人間が読む索引であり、「ADR を参照している」と「ADR を書く」を区別する情報を持たない。

### 台帳の宣言パスは漂流する

選別を通過したタスクをそのまま台帳へ転記すると、対象ファイルの記述が古いことがある。実測で 5 件（順位 228 / 193 / 412 / 176 / 145）見つかった。todo エントリは書かれた時点のファイル構成を指しており、その後のリファクタリングでは追随されない。

台帳が宣言する成果物は夜間ループの完了検証そのもの（決定 12）なので、漂流したまま登録すると **実装が正しくても「台帳が宣言する成果物に未変更のものがあります」で必ず停止する**。2026-08-16 の workflow_dispatch で実際に発生した。

## 決定 (試験運用)

### 1. 判定は順位表ではなく詳細エントリ本文で行う

`docs/todo-summary*.md` の行は候補の**列挙**にのみ使い、auto / human の判定は `docs/todo*.md` の詳細エントリ本文（動機・作業計画・完了基準）に対して行う。順位表しか読んでいない判定は、上記の過剰除外を再生産する。

**既に台帳に行がある場合は、詳細エントリ本文に加えて台帳の「注意」欄も判定材料に入れる。** 注意欄は詳細エントリの判断留保を転記する場所と定められており（台帳 § lane 割り当ての判断材料）、そこにだけ判断が書かれていることがある。実際に順位 236 をこれで取りこぼした（§ 適用実績）。

### 2. 除外は 5 クラスを順に適用し、先に当たったものを採る

| # | クラス | 除外理由 |
|---|---|---|
| 1 | グローバル `~/.claude` の編集 | リポジトリ外。夜間ループの作業ツリーに存在しない |
| 2 | 実行環境依存（hook 発火 / 実走 / `pnpm push` / e2e / 実機確認） | CI ランナー上で再現できない |
| 3 | `.github/**` など Guard 禁止パスの**書き換え** | 決定 6 の deny-list に触れる。**読むだけのタスクは除外しない** — 判定は本文の語彙ではなく「変更するファイルのパス」で行う（決定 6 § 除外クラス 3 の判定契約） |
| 4 | ADR の起票・改訂 | 設計判断であり、人間が決める |
| 5 | 本文に判断留保がある（再選定 / 検討 / 未定 / 複数案 / 着手時判断 / 要設計） | 実装内容が一意に定まらない（[ADR-072](adr-072-nightly-todo-loop.md) 決定 2「曖昧さはすべて停止側へ」） |

順序が意味を持つ。クラス 1・2 は本文の語彙で機械的に当たるが、クラス 4・5 は意味の解釈を要する。**先に機械的なクラスで落としてから解釈に進む**ことで、解釈対象を減らす。

### 3. 5 クラスを通過しても、さらに 3 種は human に残す

| 種別 | 残す理由 |
|---|---|
| **文書タスク**（convention 明記 / チェックリスト追加 / 文書化） | doc 変更はマイルストーンでまとめる運用と衝突する。夜間ループが 1 件ずつ docs PR を作ると、まとめる前提が崩れる |
| **並行性・ロックのテスト** | 並行バグは計装して両 OS で実測しないと**通るだけの偽テスト**ができる。過去にテスト自身が偽陽性を出した実例がある。無人実行に最も向かない |
| **完了基準が二択のもの**（例:「lint か型のいずれかで防ぐ」） | 実装の分岐を選ぶのは判断であり、クラス 5 と同じ扱い |

文書タスクの除外は**技術的な不可能性ではなく運用方針**である。運用が変われば見直す（決定 6）。

### 4. 台帳へ登録する前に、宣言する対象パスの実在を機械確認する

todo エントリのパスをそのまま転記しない。`Test-Path` 相当で全件確認し、漂流していたら実測値へ差し替え、**注意欄に「宣言は漂流している、実測日」を明記する**。todo エントリ側は直さない（そのエントリはタスク完了時に削除されるため、台帳が真実であればよい）。

この検査は台帳の全 auto 行に対して行う。1 行でも欠落があれば夜間ループはその順位で停止する。

**宣言は「変更されるファイル」であって「読むファイル」ではない。** テストが参照するだけのファイル（`.github/workflows/ci.yml` など）を対象欄に書くと、実装が正しくても完了検証で落ちる。参照先は注釈（丸括弧）に書く。同様に、統合テストを新設するタスクで既存の `lib.rs` を宣言してはならない — 変更されるのは新規テストファイルの方である。

**宣言の粒度は「独立した成果物」ごとに、確実に予測できる最も細かい単位にする（2026-09-04 追記）。** 完了検証が実効的に守るのは「rule 本体 + fixture + test」のような**独立した成果物の欠落**（#394）であり、同一 crate 内でどのファイルに変更が着地するかは守っていない — agent が宣言先に無意味な 1 行を足せば通るので、ファイル単位の精度は幻影で、落ちるのは正しい実装だけである。着地ファイルが実装判断で変わり得るなら、ファイルを当て推量で書かずに crate の `src/` をディレクトリ宣言（末尾 `/`、配下のいずれかの変更で充足）にし、候補ファイルは注釈に書く。新規ファイルも同様で、ファイル名を先に決めずに置き場のディレクトリを宣言する。独立した成果物が複数あるときは従来どおりそれぞれを宣言する。

**これから作る成果物は実在検査の対象外である。** 本決定の実在検査が捕まえるのは「あったものが移動した」漂流であり、新規の成果物は登録時点で存在しないのが正常である。新規の宣言は注釈に「新規」と書いて区別する（順位 426 の `src/lib-jj-helpers/tests/`（新規ディレクトリ）が例。従来の順位 360 / 361 も新規ファイルを宣言していた）。完了検証側は新規かどうかを区別しない — ディレクトリ宣言は配下のいずれかが変更一覧に現れれば充足し、新設されたディレクトリでも同じ判定になる（`lib-ledger` の `completion::evaluate` は前方一致で、事前の存在を要求しない）。

なお対象欄は `lib-ledger` が機械可読性を `cargo test` で強制しており、**注釈を除いた本体はバッククォート引用と `+` のみ**である（[ADR-072](adr-072-nightly-todo-loop.md) 決定 12）。散文で「読む対象は…」と書くと push 時の決定論ゲートで落ちる。

### 5. 割り当ての理由を注意欄に残す

なぜ auto なのか、なぜ human なのかを行に書く。理由を書かないと、**理由が失効しても行だけが残る**。順位 284 が実例で、human だった理由（未マージブランチに同タスクの実装が乗っている）は 2026-08-15 のブランチ削除で消えていたが、行は human のまま 2 日間放置された。

### 6. 自動化できる範囲とできない範囲を分ける

選別作業そのものの自動化は、**列挙と検査までに限る**。

| 工程 | 自動化 | 実装 |
|---|---|---|
| 未掲載順位の列挙（順位表 − 台帳） | ✅ 決定論 | `cli-ledger-candidates`（実装済み） |
| 詳細エントリの照合 | ✅ 決定論 | 見出し ⇄ 順位行のタイトル一致 |
| 除外クラス 1・2 の判定 | ✅ 決定論 | 本文の語彙一致 |
| 除外クラス 3 の判定 | ✅ 決定論だが**未実装** | **成果物パスを抽出し Guard 禁止パスと比較**（本文の語彙一致では不可。下記） |
| 対象パスの実在検査（決定 4） | ✅ 決定論 | パス抽出 + 存在確認 |
| 除外クラス 4・5 の判定 | ❌ | 「ADR を参照」と「ADR を書く」の区別は意味解釈 |
| 決定 3 の 3 種の判定 | ❌ | 運用方針・リスク評価を含む |
| 最終的な lane の割り当て | ❌ | 人間が決める（決定 18） |

**除外クラス 3 だけは判定の入力が違う。** クラス 1・2 は本文の語彙で当たるが、クラス 3 を同じやり方で判定すると、**Guard 禁止パスを読むだけのタスクまで落ちる**。実際に順位 360 / 361 / 454 はいずれも成果物が Rust ファイル（`src/lib-autonomy-policy/tests/*.rs`、`src/cli-nightly-task-select/src/main.rs`）で、`.github/workflows/ci.yml` は読む対象にすぎない。語彙一致で判定していれば 3 件とも誤除外していた。

したがってクラス 3 の判定契約は次のとおり。**そのタスクが変更するファイルのパスを取り、Guard 禁止パスと比較する。** 変更対象は、台帳掲載済みなら「対象ファイル」欄から、未掲載なら詳細エントリの作業計画から取る。**読むだけのファイルは注釈（丸括弧）に置かれるので判定対象に入れない**（決定 4 の「宣言は変更されるファイルであって読むファイルではない」と同じ原則）。

この判定は決定論化できるが**現時点で実装は無い**。`cli-ledger-candidates` は未掲載順位の列挙のみを行い、除外判定は持たない。上表で「未実装」と書いたのはこの意味であり、当面は人間が上の契約に沿って手で判定する。

`cli-ledger-candidates` が「候補の素材であって、昇格の判定ではない」と自ら述べているのは、この線引きによる。決定論化できない工程を LLM に委ねる場合も、**その出力は候補どまりで、台帳への `✅` は人間が付ける**。

## 帰結

### 利点

- 選別のたびに直観をやり直さなくてよい。除外理由が 5 クラス + 3 種に固定される
- 除外の内訳が数として出るため、**過剰除外に気づける**。「ADR で 88 件」という数字が出た時点で異常とわかる
- 決定 4 により、台帳登録時点でパス漂流が潰れる。夜間ループが実装後に停止する事故が前倒しで防がれる
- 決定 6 の表があるため、「この工程は自動化すべきか」を都度議論しなくてよい

### 欠点 / 留意点

- クラス 4・5 の判定は依然として解釈であり、判定者（人間または LLM）が変われば結果が揺れる。**再現性は保証されない**
- 決定 3 の文書タスク除外は、todo 全体の約 4 割（236 件中 93 件がタイトル上は文書寄り）を auto から外す。夜間ループの在庫上限を実質的に決めている
- 本 ADR 自体には決定論的な検査が無い。基準に反した割り当てを機械が拒否する仕組みは存在しない（[ADR-042](adr-042-rule-vs-mechanism-boundary.md) のいう「ルール」側にとどまる）

### 適用実績 (2026-08-17)

未掲載 236 件へ本基準を適用した結果。

| 工程 | 件数 |
|---|---|
| 未掲載（順位表 − 台帳） | 236 |
| 除外クラス 1（グローバル） | 44 |
| 除外クラス 2（環境依存） | 58 |
| 除外クラス 3（CI / workflow） | 3（後述のとおり実際にクラス 3 なのは 1 件） |
| 除外クラス 4（ADR 起票） | 22 |
| 除外クラス 5（判断留保） | 22 |
| **5 クラス通過** | **87** |
| 決定 3 により human 継続 | 大半（文書タスク約 6 割 + 並行性 4 件 + 二択 1 件） |
| **auto 候補として選別** | **25**（新規行 24 + 順位 284 の human → auto 変更 1） |
| うち差し戻し（選別ミス） | 2（順位 236 / 302。human として台帳に残る） |
| **auto の純増** | **23** |
| **最終 auto 件数** | **25**（適用前の既存 2 + 純増 23） |

**「候補 25」と「最終 25」は別の数である。** 適用前の auto は 2 件だったので、25 件を候補にして 2 件差し戻し、純増 23 で最終 25 になった。数字が一致するのは偶然であり、選別ミス率の母数は**候補の 25** の方である。

決定 4 の実在検査で **2 件の漂流を検出**した（順位 176 は `main.rs` → `rate_limit.rs`、順位 145 は `main.rs` / 不在の `lib.rs` → `presets/mod.rs`）。登録時点で修正したため、夜間ループでの停止は発生していない。

**上表のクラス 3 の 3 件は旧方式（本文の語彙一致）で落としたものなので、決定 6 の判定契約で再判定した。** 結果、実際にクラス 3（成果物が Guard 禁止パス）なのは順位 349（`pr-monitor.yml` にコメントを書き足す）の 1 件だけで、順位 220 はクラス 2（`/weekly-review` での実発火確認を含む）、順位 417 はクラス 5（キー集合の抽出方法を着手時に決める）だった。**3 件とも除外という結論は変わらず、auto 候補を取りこぼしてはいない**が、旧方式は分類の帰属を誤っていた。

**選別ミスは 2 件だった（auto 候補 25 件中）。** どちらも本 ADR を導入した push の pre-push review が検出し、auto 候補 → human へ差し戻された。差し戻した 2 行は削除せず、human lane の行として台帳に残っている。

| 順位 | 見落とした除外条件 | 実際の記述 |
|---|---|---|
| 236 | 決定 2 クラス 5（判断留保） | 注意欄に「455 と検出対象が重なる可能性があるため、**着手時にどちらかへ統合するか判断する**」と**自分で書いておきながら** `✅` を付けていた |
| 302 | 決定 3（文書タスク） | 「既存テストへの doc コメント追加」で PR タイトルも `docs(...)` prefix。挙動を変えないタスクだった |

**注目すべきは検出経路である。** 236 は除外語彙が注意欄に明示されていたので機械的な走査で当たったはずだが、私は詳細エントリ本文だけを見て台帳の注意欄を見ていなかった。**決定 1（本文で判定する）を、台帳側の記述を無視する言い訳に使っていた**。判定材料は詳細エントリ本文**と**台帳の注意欄の両方である。

加えて、**決定 4 の後段（宣言は変更されるファイルであること・機械可読形式であること）は本 ADR を書いた本人が守れなかった**。順位 360 / 361 / 310 は散文で書いたため push 時の `lib-ledger` の書式テストで落ち、順位 426 は統合テストを追加するのに `lib.rs` を宣言していた（書式テストは通るが完了検証で落ちる種類の誤り）。前者は決定論ゲートが捕まえたが、**後者を捕まえたのは人間の目視である**。宣言先が「実際に変更されるファイル」かどうかを機械が検査する手段は現状ない。

**その後、夜間ループはこの誤りで 4 回停止した**（2026-08-17 順位 228、08-23 順位 162、08-27 順位 356、09-03 順位 310。いずれも `[LEDGER_CLEANUP_BLOCK]` で、agent 到達後の停止理由として最多）。4 件とも宣言が「変更が着地するファイルの予測」になっており、予測が外れると正しい実装が落ちた。事前に機械が検査する手段は依然として無いが、**予測そのものを要らなくする**ことはできる — 決定 4 の粒度原則（2026-09-04 追記）がそれで、着地が判断次第のときはディレクトリで宣言する。2026-09-04 に順位 310 / 356 / 426 をディレクトリ宣言へ直した。

## 試験運用判断基準 (ADR-039)

- **decision trigger**: 本基準で auto へ割り当てたタスクを夜間ループが 10 件処理した時点で、(a) 完走率、(b) 停止したもののうち原因が**選別ミス**（判断留保を見落とした / パスが漂流していた / 環境依存だった）だった件数、(c) human に残した判断が後から不要とわかった件数、を測定する。
- **期限**: 2026-11-30。未判定なら延長 / 却下を判断する。
- **却下の形**: 選別ミスが（適用実績の 2 件と合わせて）3 件以上なら、除外クラスを増やすのではなく **auto の対象を「テスト追加のみ」に狭める**。基準を精緻化する方向は、判断コストが増えるだけで再現性が上がらないため採らない。**初回適用の時点で既に 2 件を使っている**（§ 適用実績）ため、残余は 1 件である。（2026-09-04 に条件が成立し、却下の形を改訂した — 次項）
- **2026-09-04 の計測と判断（却下条件の発動・却下の形の改訂）**: § 適用実績 末尾の 4 件（順位 228 / 162 / 356 / 310）はいずれも決定 4 違反（宣言パスが変更先でなかった）による選別ミスで、適用実績の 2 件と合わせて **6 件**となり却下条件（3 件以上）を満たした。ただし定めた却下の形「テスト追加のみに狭める」は、4 件中 162 / 356 がテスト追加タスクだったため**この失敗を防げない** — 失敗はタスクの種類ではなく宣言の粒度にあった。そこで却下の形を改訂する: **除外クラスを増やさず、対象も狭めず、決定 4 の粒度原則で宣言を直す**（2026-09-04 に順位 310 / 356 / 426 へ適用済み。auto lane の行は減らさない）。これは基準の精緻化ではなく単純化である — 着地ファイルを当てる判断を要らなくする方向で、判断コストは減る。**計数はここでリセットする。** 粒度原則の適用後に auto へ割り当て・再投入したタスクを夜間ループが 10 件処理した時点で再計測し、「宣言パスが変更先でなかった」選別ミスが再び 3 件以上なら、粒度原則でも防げない形と判断して当初の却下の形（テスト追加のみに狭める）を発動する。
- **緩める方向の見直し**: 決定 3 の文書タスク除外は運用方針由来なので、doc 変更のまとめ方が変われば真っ先に見直す対象になる。並行性の除外は、計装つきテストの型が確立すれば緩められる。
