# ADR-075: 着手前の前提検証 — 台帳・フィードバックの記述を実測で確かめる

## ステータス

採用 (2026-08-22)

> `docs/bugfix-batch-plan.md` (不具合修正バックログ消化計画、PR A〜L) の実施中に蓄積した知見を、計画書の退役に先立って移送したもの。計画書は ephemeral な作業計画書であり、これらの知見は本計画に固有ではないため恒久記録へ移す。

## コンテキスト

### 台帳の記述は、着手した項目のほぼ半分でずれていた

PR A〜L の 12 本で **27 項目**に着手し、**13 件で台帳と実態がずれていた**。

| 順位 | 台帳の記述 | 実際 |
|---|---|---|
| 444 | 未着手 | 本計画とは独立に PR #417 として起票済みだった |
| 328 | leftover context.json で誤 bail する | 順位 398 の guard 変更で**前提が消滅**していた |
| 347 | `cli-merge-pipeline` の欠陥 | 実装先は `cli-pr-monitor` |
| 446 | 並列 workspace のセッションが不可視 | 真因は**連結順序が時系列でないこと** |
| 336 | 時刻範囲のみで照合しない | 時刻範囲すら使わず**辞書順で最新 1 件** |
| 318 | 第 3 format 未対応 + silent 化が残る | **4 項目すべて実装済み**。本丸の既定 30 分 park も入っていた |
| 320 | check pass の誤報が残る | 決定論層は ADR-064 で**実装済み**。残件は facet/prompt 層のみ |
| 431 | `Review limit reached` を判別すればよい | 拒否の実体は **command ack** で、`markers.rs` の marker の**どちらにも一致しない** |
| 246 | CodeRabbit-only 構成で幻の CI pending が残る | 短絡は**実装済み**。さらに前提の構成自体が ADR-065 で消滅していた |
| 288(b) | `@` の非 trunk 祖先が未レビューのまま push される穴 | **(a) 側で既に閉じていた**。実在した穴は `jj bookmark list` 失敗時の fail-open |
| 233 | 根因は `[diff]` stage の `jj diff -r @` | **PR #311 で解消済み**。真因は `fix.md` の tip 限定 refresh と `review-diff.txt` の残骸 |
| 467 D-1 | 既に消えた ref で `set -euo pipefail` により step 全体が中断する | **成り立たない** — フル ref 名では exit 0。真の破綻は cwd がリポジトリでないこと (exit 128) |
| 467 D-2 | parse エラーに行番号と文脈を含める | **行番号は既に全該当箇所に入っていた**。残るのは文脈だけ |

### ずれには 2 つの質がある

**前半 (444〜246) は「起票後に実装が動いて前提が消えた」形**で、台帳が古いだけだった。台帳は起票時点のスナップショットなので、実装が動けばずれるのは避けられない。

**後半 (288(b) / 233 / 467) は違う — 起票時点から前提が誤っていた。** とりわけ 467 D-1 は、台帳・過去のフィードバック・2 件のレビューという **4 つのソースが揃って同じ誤った前提**を述べていた。しかも**誰も実測していなかった** (台帳自身が「効果確認は実走が要る」と書いていた)。実測すると前提は成り立たず、代わりに**もっと基本的な破綻**が見つかった — 掃除 step の cwd はリポジトリではなく、削除経路は過去 40 run で**一度も実行されていなかった**。

328 と 446 は、台帳どおりに実装すれば**存在しない不具合を直すか、誤った箇所を直す**ところだった。**自分が前日に書いたエントリでも同じ** — 順位 469 の Frequency 評価は実測で覆った。

### post-merge feedback も同じくずれる

台帳だけの問題ではない。feedback レポートの採用候補を起票する際、実コード確認で **2 回続けて 1 件ずつ脱落**した (PR #417 の pin テスト提案、#437 の parse エラー診断提案 — どちらも既に実装済みだった)。**feedback レポートも台帳と同じく、実装が動くほどずれる。**

## 決定

### 決定 1: 台帳・フィードバックの記述は、着手前に実装と突き合わせる

起票された記述を出発点として扱い、**結論として扱わない**。着手前に該当コードを読み、記述が現在も成立するかを確かめる。ずれていたら、記述ではなく**実態に合わせて作業範囲を決め直す** (必要ならユーザーへ確認する)。

### 決定 2: 複数ソースの一致は、正しさの証拠にならない

同じ前提を述べるソースが何件あっても、**どれも実測していなければ証拠は 0 件**である。「4 ソースが同一指摘」は着手の根拠にはなるが、前提が真である根拠にはならない。

**実測で分かることは実測する。** 467 D-1 は、使い捨てリポジトリで ref 削除を 1 回試せば 5 秒で分かる話だった。

### 決定 3: シグネチャ・戻り値・引数の数を変えたら、呼び出し元と下流の `match` を必ず追う

**局所的には正しい変更が、周囲の構造が変わったことで別の意味を持つ。** CodeRabbit の Major 指摘 2 件が同じ構造だった。

- [PR #418](https://github.com/aloekun/claude-code-hook-test/pull/418): `FixCommitState::None` を返す変更が、下流 `decide_repush_action` の `(HasChange, _, true) => AutoPush` 経路を開いた (分離コミットなしで push される)
- [PR #421](https://github.com/aloekun/claude-code-hook-test/pull/421): 走査 source を単数→複数にしたのに `?` を残し、1 ディレクトリの失敗で全 workspace 分が失われる構造になった

### 決定 4: 識別子を照合キーにするなら、一意性の根拠をリポジトリ全体で確認する

[PR #420](https://github.com/aloekun/claude-code-hook-test/pull/420) で bookmark 名を一意キーと仮定したが、`claude/nightly-<順位>` は夜間ループが再利用する。CodeRabbit はリポジトリ全体を走査して気づき、こちらは変更箇所の周辺しか見ていなかった。

同型として、**外部 SaaS の marker を流用する前に、自分が観測する comment class の実データを見る**。順位 431 で `markers.rs` の `RATE_LIMIT_MARKERS` をそのまま使ったが、それは CodeRabbit の **walkthrough placeholder** 向けで、`@coderabbitai review` への直接の応答である **command ack** には一致しない。実データを `gh api` で読むまで気づかなかった (読まずに land していれば、**レート制限を検知できない検知機構**ができていた)。同じ SaaS でも comment class ごとに文言体系が違う。

### 決定 5: doc に「機構がある」と書いたら、その機構が実在するか確かめる

3 度やった — `RUN_REPORT_FILE_NAME` の pin テスト (存在しなかった / [#418](https://github.com/aloekun/claude-code-hook-test/pull/418) で追加)、fix step が書いた「3 crate を共通化」(1 crate だけだった)、`sort_key` の mtime tie-break (`source_path` へ変えた後も doc が残っていた)。

## 帰結

### 得られるもの

- **存在しない不具合を直す作業が消える。** 本計画では 13 件のうち少なくとも 5 件 (318 / 320 / 246 / 288(b) / 233) が「既に実装済み」で、確認せず着手すれば全て無駄になっていた
- **真の不具合が見つかる。** 前提を疑って実測した結果、台帳が想定していたより深刻な破綻が 2 件見つかった (467 D-1 の exit 128、322 の `__*` パターンがデッド)

### 引き受けるコスト

着手前の確認そのものに時間がかかる。ただし本計画の実績では、**確認を怠って誤った箇所を直すコストのほうが常に大きかった** (誤った実装 + レビュー + 差し戻し)。

### 本 ADR で扱わないこと

- **どう実測するか**の手順は扱わない。対象ごとに違う (コードを読む / スタブで走らせる / 実データを `gh api` で取る / 使い捨てリポジトリで試す)
- **機械化**は扱わない。前提の検証は対象依存で、決定論層に落とせる形が今のところ見えていない。落とせるものが見つかれば個別に lint / hook 化する ([ADR-042](adr-042-rule-vs-mechanism-boundary.md) の境界基準に従う)
